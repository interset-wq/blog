
# 认证、授权与 Web 安全

## 认证（Authentication）与授权（Authorization）

### 认证 vs 授权

| 概念 | 回答的问题 | 时机 |
| --- | --- | --- |
| **认证（Authentication）** | "你是谁？"（验证身份） | 必须先于授权 |
| **授权（Authorization）** | "你被允许做什么？"（确定权限） | 认证之后 |

> 在后台代码中，授权通常通过**检查用户角色或权限的中间件**来执行，然后再授予访问。

### 认证的三种因素

1. **你知道的（Something you know）**：密码、PIN、安全问题答案。
2. **你拥有的（Something you have）**：接收短信验证码的手机、认证器应用 token。
3. **你是什么（Something you are）**：指纹、面部识别（生物特征）。

### 授权中的常见角色

- **标准用户（Standard User）**：受限的自助服务。
- **编辑（Editor）**：内容管理。
- **管理员（Admin）**：完整系统访问。

## CSRF（跨站请求伪造）

**CSRF**：恶意网站诱使已认证用户的浏览器向后台服务器发送**非预期请求**，利用浏览器**自动附加 Cookie** 的特性。

### 攻击流程

1. 用户登录 `trusted-bank.com`。
2. 访问 `evil-hacker-site.com`。
3. 恶意网站向银行提交隐藏表单。
4. 银行服务器看到有效会话 Cookie，执行该请求。

### 防御手段

| 手段 | 说明 |
| --- | --- |
| `SameSite=Strict` | 请求来自第三方网站时，浏览器**绝不发送**该 Cookie |
| `SameSite=Lax` | 仅在用户**安全导航**到目标站（点击链接）时发送 Cookie；阻止跨站表单提交 |
| **CSRF 令牌** | 服务器生成随机不可预测的令牌嵌入表单，客户端每次状态变更请求都必须携带。恶意网站无法从前端读取令牌，伪造请求会校验失败 |

## JWT（JSON Web Token）

**JWT**：登录成功后服务器签发的一种**数字签名令牌**。客户端存储它，并在每次后续请求中携带，实现**无状态认证**（无需服务器端会话存储）。

### JWT 结构

三个用点分隔的 Base64URL 编码部分：

1. **Header（头部）**：令牌类型（`JWT`）和签名算法（如 `HS256`）。
2. **Payload（载荷）**：关于用户的声明（用户 ID、用户名、角色）。**未加密**，所以**绝不要存储密码或敏感数据**。
3. **Signature（签名）**：Header + Payload + 服务器密钥的哈希，防止篡改。


> 若用户篡改 Payload，签名将不匹配，服务器以 `401 Unauthorized` 拒绝请求。

### 用 `jsonwebtoken` 签发与验证

```bash
npm install jsonwebtoken
```

```js
const jwt = require("jsonwebtoken");

const SECRET = process.env.JWT_SECRET || "change-me"; // 生产用 .env
const payload = { userId: 42, username: "jane", role: "admin" };

// 1. 签发：payload + 密钥 + 过期时间
const token = jwt.sign(payload, SECRET, { expiresIn: "1h" });
console.log(token); // xxx.yyy.zzz（三段 Base64URL）

// 2. 验证：签名不匹配会抛错
try {
  const decoded = jwt.verify(token, SECRET);
  console.log(decoded.userId); // 42
} catch (err) {
  console.error("无效或过期的 token:", err.message);
}

// 3. 作为 Express 中间件做认证
function authenticate(req, res, next) {
  const header = req.headers.authorization; // "Bearer <token>"
  if (!header) return res.status(401).json({ error: "No token" });
  const token = header.split(" ")[1];
  try {
    req.user = jwt.verify(token, SECRET);
    next();
  } catch {
    res.status(401).json({ error: "Invalid token" });
  }
}

app.get("/profile", authenticate, (req, res) => {
  res.json({ user: req.user }); // 只有携带有效 token 才能访问
});
```

## Passport.js

**Passport.js**：Node.js 的认证中间件。标准化认证流程，处理底层细节，让开发者专注于业务逻辑。

### 策略（Strategies）

模块化插件，实现特定认证方法。有 500+ 种策略可用：

- `passport-local`：用户名/密码
- `passport-jwt`：JWT
- `passport-google-oauth20`：Google 登录
- `passport-facebook`、`passport-github2`：Facebook / GitHub

### 完整登录流程

```js
const passport = require("passport");
const LocalStrategy = require("passport-local").Strategy;
const bcrypt = require("bcrypt");

// 1. 注册策略：定义如何验证用户名/密码
passport.use(
  new LocalStrategy(async (username, password, done) => {
    try {
      const user = await db.getUser(username);
      if (!user) return done(null, false, { message: "用户不存在" });
      const ok = await bcrypt.compare(password, user.passwordHash);
      if (!ok) return done(null, false, { message: "密码错误" });
      return done(null, user); // 认证成功
    } catch (err) {
      return done(err);
    }
  })
);

// 2. 初始化 Passport
app.use(passport.initialize());
app.use(passport.session()); // 若用会话 Cookie

// 3. 登录路由（认证成功才进入 handler）
app.post(
  "/login",
  passport.authenticate("local", { failureRedirect: "/login" }),
  (req, res) => {
    res.redirect(`/welcome/${req.user.username}`);
  }
);

// 4. 保护路由
app.get("/profile", (req, res) => {
  if (!req.user) return res.status(401).json({ error: "请先登录" });
  res.json({ user: req.user });
});
```

> 认证成功后，Passport 会在会话 Cookie 中存储一段用户数据，并把认证后的用户对象挂到 `req.user`。

## 安全 vs 隐私

- **安全（Security）**：保护系统和数据免受未授权访问的**技术防御机制**。安全是门上的锁。
- **隐私（Privacy）**：关于个人数据如何被收集、使用和分享的**治理**。隐私是窗上的帘。

> 可以只有安全而没有隐私（被锁定的数据库仍可能售卖你的数据），但不能只有隐私而没有安全（未受保护的数据无法保持私密）。

## 同源策略与 CORS

### 源（Origin）

由三个部分定义：**协议**（如 `https`）+ **域名**（如 `example.com`）+ **端口**（如 `443`）。三者全部匹配才属于同一源。

### 同源策略

浏览器安全规则：阻止一个源的脚本读取另一个源的数据，防止恶意站点窃取其他已打开标签页中的数据。

### CORS（跨域资源共享）

一种机制，允许服务器通过设置 HTTP 头，为受信任的源放宽同源策略。

- **开发环境**：`app.use(cors())` 允许所有源。
- **生产环境**：传入带 `origin` 白名单的 `corsOptions` 对象：

```js
const corsOptions = {
  origin: ["https://mysite.com", "https://api.mysite.com"],
};
app.use(cors(corsOptions));
```

## HTTPS

**HTTPS**：带 TLS（传输层安全协议）加密的 HTTP。TLS 取代了更旧的 SSL 协议。

### HTTPS 的三重保证

1. **加密（Encryption）**：客户端与服务器间传输的数据对第三方不可读。
2. **认证（Authentication）**：受信任 CA 颁发的数字证书确认服务器身份。
3. **数据完整性（Data integrity）**：消息在传输中被改动即可被检测。

> 现代浏览器 API（地理位置、推送通知、摄像头访问）都要求 HTTPS。

## Helmet.js 与安全中间件

**Helmet.js**：安全中间件集合，通过自动设置、修改或移除 HTTP 响应头来保护 Express 应用。

```js
const helmet = require("helmet");
const cors = require("cors");
const morgan = require("morgan");

app.use(helmet());                       // 安全响应头
app.use(cors({ origin: ["https://mysite.com"] })); // 受控跨域
app.use(morgan("combined"));             // 请求日志

// CSRF 防御要点
// 1) 会话 Cookie 设置 HttpOnly + SameSite=Strict
// 2) 状态变更请求携带随机 CSRF token，服务端校验
```

### Helmet 主要保护能力

| 能力 | 说明 |
| --- | --- |
| 移除 `X-Powered-By` | 防止攻击者得知服务器技术栈 |
| 设置 `Content-Security-Policy` | 限制脚本、图片、样式的加载来源，缓解 XSS 攻击 |
| 设置 `X-Frame-Options: SAMEORIGIN` | 阻止点击劫持（防止你的站点被嵌入外部 iframe） |
| 设置 `Strict-Transport-Security` | 强制浏览器使用 HTTPS，保护数据不被截获 |

## 安全问题为何会发生

- **交付压力**：团队为赶工期跳过安全评审，带着漏洞上线。
- **复杂系统集成**：第三方库或云服务引入开发团队未编写的漏洞（供应链风险）。
- **配置管理不善**：保留默认设置（默认管理员密码、开放端口）导致系统暴露。
- **人为错误**：钓鱼攻击利用点击恶意链接的员工骗取凭据。
- **组织并购**：合并不同代码库和基础设施，暴露不匹配的安全策略和遗留漏洞。

## Cookie：存储、安全标志与隐私

### Cookie 如何存储

服务器发送 `Set-Cookie` 头 → 浏览器保存到磁盘 → 之后每次请求自动返回给该源。

### 安全标志

| 标志 | 作用 |
| --- | --- |
| `HttpOnly` | 阻止 JavaScript 读取 Cookie 值，防止基于 XSS 的会话窃取 |
| `Secure` | 仅限 HTTPS 连接传输，防止在公共网络上被截获 |
| `SameSite=Strict` | 阻止浏览器在任何跨站请求中发送该 Cookie，完全阻断 CSRF |
| `SameSite=Lax` | 允许顶层导航（如点击链接）发送，阻止跨站表单提交和 API 调用 |

### Cookie 类型

- **第一方 Cookie**：作用域为当前访问的站点。
- **第三方 Cookie**：由广告网络在数千站点间设置，用于追踪行为、构建用户画像。现代浏览器默认拦截。

### GDPR 合规

隐私法律要求 Cookie 同意横幅，赋予用户拒绝非必要追踪 Cookie 的法律权利。

## 常见安全威胁与缓解

| 威胁 | 说明 | 缓解措施 |
| --- | --- | --- |
| **钓鱼（Phishing）** | 冒充可信公司的欺诈邮件窃取凭据 | 安全意识培训；部署邮件认证协议，阻止恶意邮件到达收件箱 |
| **恶意软件**（病毒、间谍软件、勒索软件） | 勒索软件加密文件并索要赎金 | 自动更新；防恶意软件 |
| **撞库（Credential stuffing）** | 攻击者在不同网站批量尝试海量已泄露的用户名/密码组合 | 主要缓解：**多因素认证（MFA）**，需二次验证（OTP 或认证器） |
| **DDoS（分布式拒绝服务）** | 攻击者用虚假流量淹没服务器使其崩溃 | 云端流量过滤服务：Cloudflare、Akamai、AWS Shield |
| **内部威胁** | 恶意或粗心的员工窃取/泄露数据 | **最小权限原则**（只授予工作所需权限）；监控系统日志 |

## CSP 与 Permissions-Policy

### CSP（内容安全策略）

HTTP 响应头，为脚本、样式和图片**白名单**允许的源域名。浏览器收到 CSP 头后，会阻止任何来自非白名单域名的资源加载。

- `script-src` 指令指定哪些域名可执行 JavaScript，阻止 XSS 注入攻击。

### Permissions-Policy

HTTP 头，为页面和嵌入的 iframe 启用或禁用浏览器功能和设备硬件。取代了旧的 `Feature-Policy` 头。

- `camera=(self)`：仅限本页源使用摄像头。
- `geolocation=()`：对所有用户完全禁用定位。

> 两者结合提供分层保护：CSP 阻止代码注入，Permissions-Policy 阻止未授权的硬件访问。

## 用户隐私基本概念

| 概念 | 说明 |
| --- | --- |
| **PII（个人身份信息）** | 能直接或间接识别个人的数据 |
| — 直接标识符 | 全名、家庭住址、身份证号 |
| — 间接标识符 | IP 地址、设备序列号、精确位置历史 |
| **保密性** | 通过加密和访问控制保护 PII 免遭未授权访问 |
| **数据最小化** | 只收集完成特定任务所需的最少量 PII |
| **目的限制** | 为某一原因收集的数据，未经用户新同意不得挪作他用（如卖给广告网络） |
| **追踪** | 使用脚本、设备指纹、浏览器历史日志持续监控用户在线行为 |
| **被遗忘权（数据擦除）** | 用户关闭账户后，可依法要求永久删除公司数据库中所有个人记录的法律权利 |

## `.env` 文件与 `dotenv`

### `.env` 文件

项目根目录的纯文本文件，以键值对存储配置机密（API 密钥、数据库密码、端口号）。**始终加入 `.gitignore`** 以防机密进入版本控制。

### `dotenv` 包

启动时读取 `.env` 文件，把值注入 `process.env`：

```js
require("dotenv").config();

const port = process.env.PORT || 5000;
const apiKey = process.env.API_KEY;
```

### 两大好处

1. **安全**：凭据不进入源代码。
2. **灵活**：同一代码库通过在不同服务器上替换 `.env` 文件，即可在不同环境（开发、预发布、生产）表现不同。

## 地区隐私法律与合规

| 法律 | 管辖范围 | 核心要求 |
| --- | --- | --- |
| **GDPR** | 欧盟内个人 | 追踪前需明确**主动同意**（不允许预勾选）；赋予查看和永久删除数据的权利；违规重罚 |
| **CCPA / CPRA** | 加州居民 | 侧重**退出**（opt-out）而非主动同意；首页需有可见的"Do Not Sell My Personal Information"链接 |
| **COPPA** | 美国 13 岁以下儿童 | 收集儿童数据前需明确隐私政策 + 可验证的父母同意 |
| **DPA** | 英国 | 与英国 GDPR 配套，赋予访问和删除数据的权利 |

> 其他国家：尼日利亚 NDPA（尼日利亚数据保护法）、印度 DPDP Act（数字个人数据保护法）。

### 全球化团队的合规步骤

1. 构建**按位置感知**的同意横幅，根据用户地理位置显示相应 Cookie 通知。
2. 实现自动化的 **DSAR（数据主体访问请求）**系统，依法查找、导出或永久擦除用户数据。
3. 践行**数据最小化**，用**年龄验证门**防止对未成年人的未授权追踪。
4. 指定**数据保护官（DPO）**，监督隐私架构并作为与监管机构的主要联系人。
