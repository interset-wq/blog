# 软件测试与软件开发生命周期

软件测试是软件开发生命周期中保证质量的关键环节。要理解测试，先要清楚它在整个开发流程中的位置。

## 一、软件开发生命周期（SDLC）

软件开发生命周期的不同阶段：

| 阶段 | 说明 |
|---|---|
| 规划阶段 | 开发团队从利益相关者收集需求 |
| 设计阶段 | 软件团队拆解需求，决定最佳解决方案 |
| 实现阶段 | 将需求拆分为可管理任务并实现 |
| 测试阶段 | 包括手动和自动测试新功能；有时团队在整个开发阶段测试应用，及时发现并修复问题 |
| 部署阶段 | 将新变更部署到构建或测试环境 |
| 维护阶段 | 修复生产应用中客户反馈的问题 |

### 生命周期模型

| 模型 | 说明 |
|---|---|
| **瀑布模型** | 每个阶段完成后才能进入下一阶段，顺序严格、文档驱动 |
| **敏捷模型** | 关注迭代开发，将工作拆分为冲刺（Sprint），持续交付 |

> 现代 Web / 前端项目多采用敏捷迭代，配合 CI/CD 持续集成部署。

### TDD、BDD 与 SDD

- **TDD（测试驱动开发）**：强调**先写测试**，再开发功能。在开发过程中提供实时反馈，保证代码可测、符合预期。
- **BDD（行为驱动开发）**：将**测试场景与业务目标对齐**。测试场景应使用技术和非技术人员都能理解的语言，**Gherkin** 是此类语法示例。
- **SDD（Specification-Driven Development，规格驱动开发）**：强调**先写规格说明（Specification）**，再据此开发。规格明确描述「做什么、边界是什么、如何验收」，代码只是规格的实现。

BDD 测试框架：Cucumber、JBehave、SpecFlow。

Gherkin 语法示例：

```gherkin
Feature: 用户登录
  Scenario: 输入正确密码可以登录
    Given 用户已注册
    When 用户输入正确的用户名和密码
    Then 系统跳转到首页
```

### SDD 在 AI Agents 时代为何流行

随着 AI 编程 Agent（如 Cursor、Copilot、Claude Code 等）普及，**规格成为驱动 Agent 编码的核心输入**——Agent 无法像人一样「领会意图」，它依赖清晰、可验证的规格来产出符合预期的代码：

- **规格即提示词**：把 PRD、接口契约、验收标准写成结构化的 spec，Agent 据此生成代码，大幅减少返工。
- **可验收**：规格包含可测试的验收条件，产出能用自动化测试验证，而非「看起来差不多」。
- **人审规格、Agent 写码**：开发者把精力放在定义正确的规格上，编码交给 Agent，分工更清晰。
- **演进 TDD**：TDD 的「先写测试」与 SDD 的「先写规格」结合——规格驱动设计，测试保障规格被正确实现。

一个简单的规格示例：

```markdown
# 用户登录规格
- 输入：邮箱 + 密码
- 行为：验证凭据，成功返回 token，失败返回 401
- 边界：邮箱格式非法时拒绝；密码错误 5 次后锁定 15 分钟
- 验收：E2E 通过登录流程；单元测试覆盖上述边界
```

## 二、手动测试与自动测试

- **手动测试**：测试人员手动检查应用的每个部分，测试不同功能确保其正常工作；发现错误后反馈给软件团队修复。适合探索性、可用性场景。
- **自动测试**：通过编写单独程序自动检查应用是否按预期运行。可重复、快、适合回归；需要维护测试代码。

> 实践中两者互补：自动化覆盖核心与回归，手动补充自动化难覆盖的体验类问题。

## 三、单元测试（Unit Test）

**单元测试（Unit Test）** 测试每个函数，确保其按预期工作。单元测试也可作为应用文档，表示代码的预期行为。

- **单一职责原则**：建议保持每个函数小且只负责一件事，便于测试。
- **常见 JS 测试框架**：**Jest**、**Mocha**、**Vitest**。Jest 是流行的单元测试框架。

示例：先创建一个返回新格式字符串的函数：

```js
export function getFormattedWord(str) {
  if (!str) return '';
  return str.charAt(0).toUpperCase() + str.slice(1);
}
```

在单独的 `getFormattedWord.test.js` 文件中编写测试：

```js
import { getFormattedWord } from "./getFormattedWord.js";
import { test, expect } from "jest";

test('capitalizes the first letter of a word', () => {
  expect(getFormattedWord('hello')).toBe('Hello');
});
```

### expect 与匹配器

- **expect 函数**：用于测试一个值。
- **匹配器（matcher）**：检查值是否符合预期的函数。上例中的匹配器是 `toBe()`。

Jest 常用匹配器：

| 匹配器 | 作用 |
|---|---|
| `toBe(x)` | 严格相等（`===`） |
| `toEqual(obj)` | 递归相等（对象/数组内容） |
| `toBeNull()` / `toBeUndefined()` | 判空 / 未定义 |
| `toBeTruthy()` / `toBeFalsy()` | 真值 / 假值 |
| `toContain(item)` | 数组 / 字符串包含 |
| `toHaveLength(n)` | 长度 |
| `toThrow()` | 抛出异常 |

### 运行配置

```bash
$ npm i jest
```

在 `package.json` 添加脚本：

```json
"scripts": {
  "test": "jest"
}
```

运行：`npm run test`。

## 四、单元测试中的断言（Assertion）

**断言（Assertion）**用于测试代码是否按预期运行。

- **断言库**：**Chai** 是常用断言库，其他常见 JS 断言库有 `should.js`、`expect.js`。

使用 Chai 的断言示例——检查 `addThreeAndFour` 函数返回值是否等于 7：

```js
assert.equal(addThreeAndFour(), 7);
```

> 最佳实践：无论使用哪个断言库，都应编写清晰的断言和失败信息，帮助理解测试失败原因。

## 五、模拟（Mock）、存根（Stub）与伪造（Fake）

用于隔离被测代码的外部依赖：

| 技术 | 说明 | 示例 |
|---|---|---|
| **模拟（Mock）** | 用假数据替代真实数据，模拟真实组件行为 | 模拟 API 响应，避免持续调用 API |
| **存根（Stub）** | 返回预定义响应或虚拟数据的对象，模拟预期行为 | 存根数据库连接，无需依赖真实数据库 |
| **伪造（Fake）** | 简化的真实组件版本，无复杂性或副作用 | 内存数据库模拟数据库操作，比真实更快 |

## 六、功能测试（Functional Test）与非功能测试（Non-Functional Test）

- **功能测试（Functional Test）**：检查应用功能是否按预期工作，针对多种场景测试系统整体。
- **非功能测试（Non-Functional Test）**：关注性能和可靠性等方面。
- **冒烟测试（Smoke Test）**：在开始更广泛测试前，对系统进行基本或关键问题的初步检查。

## 七、端到端测试（End-to-End Test，E2E）

**端到端测试（End-to-End Test，E2E）** 从用户视角测试真实场景，确保应用行为正确且用户可预测。但设置、设计和维护耗时。

- **E2E 框架**：**Playwright**（微软开发，流行）、**Cypress**、**Selenium**、**Puppeteer**。

Playwright 示例（来自 freeCodeCamp）：`beforeEach` hook 在每个测试前运行；测试检查捐赠者菜单栏中有支持者链接，以及头像周围有特殊样式边框：

```js
test.beforeEach(async ({ page }) => {
  execSync("node ./tools/scripts/seed/seed-demo-user --set-true isDonating");
  await page.goto("/donate");
});

test("The menu should have a supporters link", async ({ page }) => {
  const menuButton = page.getByTestId("header-menu-button");
  const menu = page.getByTestId("header-menu");

  await expect(menuButton).toBeVisible();
  await menuButton.click();
  await expect(menu).toBeVisible();
  await expect(page.getByRole("link", { name: "Supporters" })).toBeVisible();
});

test("The Avatar should have a special border for donors", async ({ page }) => {
  const container = page.locator(".avatar-container");
  await expect(container).toHaveClass("avatar-container gold-border");
});
```

要点：`page` 模拟浏览器、`getByTestId` / `getByRole` 定位元素、`toBeVisible` 断言可见、`toHaveClass` 断言类名。

## 八、可用性测试（Usability Test）

**可用性测试（Usability Test）** 让真实用户与应用交互，发现设计、用户体验或功能问题，关注用户对应用的直观感受。

四种常见类型：

| 类型 | 说明 |
|---|---|
| 探索性（Exploratory） | 用户交互应用不同功能，了解工作方式 |
| 比较性（Comparative） | 将应用体验与市场上类似应用比较 |
| 评估性（Evaluative） | 研究应用使用的直观性 |
| 验证性（Validation） | 识别阻碍用户有效使用的重大问题 |

工具：Loop11、Maze、Userbrain、UserTesting、UXTweak。

## 九、兼容性测试（Compatibility Test）

**兼容性测试（Compatibility Test）** 确保应用在不同计算环境中正常工作。不同类型：

| 类型 | 说明 |
|---|---|
| 向后兼容（Backward Compatibility） | 软件兼容早期版本 |
| 向前兼容（Forward Compatibility） | 软件能兼容未来版本 |
| 硬件兼容（Hardware Compatibility） | 在不同硬件配置下正常工作 |
| 操作系统兼容（OS Compatibility） | 在 macOS、Windows、Ubuntu、Fedora 等系统运行 |
| 网络兼容（Network Compatibility） | 适应不同网络速度、协议、安全设置 |
| 浏览器兼容（Browser Compatibility） | 在 Chrome、Safari、Firefox 等浏览器中一致运行 |
| 移动兼容（Mobile Compatibility） | 在各种 Android / iOS 设备（手机、平板）上运行 |

## 十、性能测试（Performance Test）

**性能测试（Performance Test）** 测试应用在不同负载下的速度、响应性、可扩展性和稳定性，目标是解决性能瓶颈。

不同类型：

| 类型 | 说明 |
|---|---|
| 负载测试（Load Test） | 正常和峰值负载下的表现 |
| 压力测试（Stress Test） | 极端负载下观察系统响应 |
| 浸泡测试 / 耐力测试（Soak / Endurance Test） | 长时间高负载测试 |
| 突发测试（Spike Test） | 剧烈增加和减少负载，分析反应 |
| 断点测试 / 容量测试（Breakpoint / Capacity Test） | 逐步增加负载直到系统失败或性能下降 |

## 十一、安全测试（Security Test）

**安全测试（Security Test）** 识别漏洞和弱点。

安全原则：**机密性**（防止信息泄露）、**完整性**（防止篡改）、**认证**（验证身份）、**授权**（控制操作权限）、**可用性**（保证可访问）、**不可否认性**（提供交付与身份验证证据）。

常见安全威胁：

- **跨站脚本攻击（XSS）**：向网页注入恶意脚本，在受害者浏览器上下文中执行。
- **SQL 注入**：向数据库注入恶意代码。
- **拒绝服务攻击（DoS）**：用大量请求淹没网站，使其变慢或崩溃。

安全测试工具类别：

| 类别 | 说明 |
|---|---|
| 静态应用安全测试（SAST） | 评估源代码，识别漏洞 |
| 动态应用安全测试（DAST） | 与应用前端交互发现弱点，无法访问源代码 |
| 渗透测试（Pentest） | 模拟网络攻击，识别系统漏洞 |

## 十二、A/B 测试（A/B Test）

**A/B 测试（A/B Test）** 比较页面或应用的两个版本，研究哪个表现更好，也称桶测试或分割测试。帮助做数据驱动的决策，持续改进用户体验。

工具：GrowthBook、LaunchDarkly。

## 十三、Alpha、Beta 与验收测试（Acceptance Test）

初步开发和测试完成后，让测试人员和真实用户测试应用：

- **Alpha 测试（Alpha Test）**：由选定测试人员进行，确保发布前无错误；属于验收测试，使用**白盒**和**黑盒**测试技术。
- **Beta 测试（Beta Test）**：向真实用户开放，用户可交互并提供反馈；也是用户验收测试的一种。
- **验收测试（Acceptance Test）**：确保软件满足业务需求和用户需求，方可发布。
- **黑盒测试（Black-box Test）**：只关注应用的预期行为，不关心内部实现。
- **白盒测试（White-box Test）**：测试人员了解内部组件并对其进行测试。

## 十四、回归测试（Regression Test）

**回归（Regression）**指新变更无意中破坏了现有功能。**回归测试（Regression Test）** 帮助发现回归问题——通过重新运行功能测试，确保应用各部分仍按预期工作。

- 工具：Puppeteer、Playwright、Selenium、Cypress。
- 技术：
  - **单元回归测试（Unit Regression）**：每次重大变更或修复后，测试需覆盖的项目列表；
  - **部分回归测试（Partial Regression）**：针对特定方面的针对性测试，确保新变更未破坏；
  - **完整回归测试（Full Regression）**：对代码库所有功能运行测试，最耗时且详尽。
- **重测（Retest）**：检查已知问题是否解决。与回归测试不同——回归测试寻找因代码变更引入的**未知**问题。

## 十五、测试在生命周期中的位置

各类测试分布在生命周期的不同阶段：

- 单元测试在**实现阶段**即时编写（配合 TDD）。
- 集成 / 功能 / E2E 测试在**测试阶段**执行。
- **回归测试**在每次变更后运行，贯穿实现到维护阶段。
- Alpha / Beta / 验收测试在**部署前**完成，确保满足业务需求。

## 核心总结

1. SDLC 六阶段：规划 → 设计 → 实现 → 测试 → 部署 → 维护；模型有瀑布与敏捷。
2. TDD 先写测试后实现；BDD 用 Gherkin 对齐业务目标；SDD 先写规格，是 AI Agents 时代驱动编码的主流方式。
3. 手动 + 自动测试互补；自动化适合单元与回归。
4. 单元测试用 Jest/Vitest/Mocha + 匹配器；断言库如 Chai；Mock / Stub / Fake 隔离外部依赖。
5. E2E（Playwright/Cypress）从用户视角测真实场景；可用性、兼容性、性能、安全各有侧重。
6. Alpha/Beta 面向发布；黑盒/白盒是测试视角；回归测试防新变更破坏旧功能。
7. 不同测试类型分布在生命周期不同阶段，回归测试贯穿变更周期。
