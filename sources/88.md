## MVT 架构详解

Django 遵循 **MVT**（**Model–View–Template**）分层架构。它是经典 **MVC**（Model–View–Controller）的一种变体：**Django 的 View 承担了 Controller 的职责**，因此叫 MVT 而不是 MVC。

| 层 | 职责 | 对应文件 |
|---|---|---|
| **M**odel | 数据结构与数据库表 | 各 app 的 `models.py` |
| **V**iew | 业务逻辑：收请求 → 查数据 → 返回响应 | 各 app 的 `views.py` |
| **T**emplate | HTML 页面 + 模板语言 DTL | 各 app 的 `templates/` |
| URLconf | URL → 视图的映射（路由器） | `urls.py` |

> 一句话：**URL 把请求路由给 View，View 用 Model 读写数据，再把结果交给 Template 渲染成 HTML 返回。**

### 一次请求的完整生命周期

```
浏览器发起 GET /books/
        │
        ▼
项目级 urls.py（URLconf）按规则匹配 URL
        │  找到对应的视图
        ▼
View 执行业务逻辑
        │  用 Model（ORM）查询
        ▼
拿到数据对象 / 列表
        │
        ▼
交给 Template 渲染
        │  把模板占位符替换成真实数据，生成 HTML
        ▼
返回 HttpResponse
        ▼
浏览器展示页面
```

### 每一层长什么样

**Model（数据层）** —— 定义"一张表长什么样"：

```python
# app/models.py
from django.db import models

class Book(models.Model):
    title = models.CharField(max_length=200)
    published = models.DateField(null=True, blank=True)

    def __str__(self):
        return self.title
```

**View（业务层）** —— 接收请求、查数据、返回响应（函数视图 FBV）：

```python
# app/views.py
from django.shortcuts import render
from .models import Book

def book_list(request):
    books = Book.objects.all()              # 用 Model 查数据
    return render(request, 'books.html', {'books': books})   # 交给 Template
```

**URLconf（路由层）** —— 把 URL 映射到视图：

```python
# app/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path('books/', views.book_list, name='books'),
]
```

**Template（表现层）** —— 只负责展示，不写业务逻辑：

```html
<!-- app/templates/books.html -->
{% for book in books %}
  <p>{{ book.title }} · {{ book.published|date:'Y-m-d' }}</p>
{% empty %}
  <p>No books.</p>
{% endfor %}
```

> 分层铁律：**Model 只管数据，View 只管业务，Template 只管展示，URLconf 只管路由**。业务逻辑永远不写进模板。

## 初始化一个 Django 项目

### 完整命令序列

```bash
uv init
uv add django
# 初始化django项目
django-admin startproject mysite .
# 创建app，创建之后需要在settings.py中挂载
python manage.py startapp myapp
# 为自定义模型生成迁移并建表
python manage.py makemigrations
python manage.py migrate
# 创建管理员
python manage.py createsuperuser
python manage.py runserver
```

浏览器打开 <http://127.0.0.1:8000/>，一个能跑的 Django 项目就诞生了。

`django-admin startproject mysite .`** —— 生成项目骨架：

```
mysite/                  # 项目根（manage.py 所在目录）
├── manage.py            # 命令行入口：runserver、migrate、startapp 等
└── mysite/              # 项目配置包（settings/urls）
    ├── __init__.py
    ├── settings.py      # 全部配置
    ├── urls.py          # 项目级 URLconf
    ├── wsgi.py          # WSGI 入口（同步部署）
    └── asgi.py          # ASGI 入口（异步/WebSocket）
```

- **末尾的 `.`** 表示"在当前目录生成"，`manage.py` 落在当前目录；不加 `.` 会生成一层 `mysite/mysite/` 嵌套目录。

`python manage.py startapp myapp`** —— 创建app：

```
mysite/                  # 项目根（manage.py 所在目录）
├── manage.py            # 命令行入口：runserver、migrate、startapp 等
└── mysite/              # 项目配置
    myapp/               # app
    ├── __init__.py
    ├── admin.py     # 注册模型到后台
    ├── apps.py      # 应用配置
    ├── models.py    # 数据模型（M 层）
    ├── tests.py     # 测试
    ├── views.py     # 视图（V 层）
    └── migrations/  # 迁移文件目录
```

> **项目（project）vs 应用（app）**：项目是"站点"（配置 + 路由），应用是"功能模块"（博客、评论、用户…）。一个项目可含多个应用，一个应用也可被多个项目复用。

**注册应用** —— 新建的 app 要生效，必须在 `settings.py` 的 `INSTALLED_APPS` 里登记：

```python
# mysite/settings.py
INSTALLED_APPS = [
    'myapp',                      

    'django.contrib.admin',       
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]
```

### 迁移详解：makemigrations 与 migrate

`makemigrations` 是初始化流程的关键一步：你在 `models.py` 定义模型后，要把"模型 → 数据库表"落地，需要两条命令配合。

```bash
python manage.py makemigrations   # 生成迁移文件（不碰数据库）
python manage.py migrate          # 把迁移应用到数据库（真正建表）
```

| 命令 | 做什么 | 是否动数据库 |
|---|---|---|
| `makemigrations` | 对比模型与迁移记录，**生成迁移文件**（如 `myapp/migrations/0001_initial.py`） | 否，只生成"改动说明书" |
| `migrate` | 读取迁移文件，**把变更实际应用到数据库**（建表、加列） | 是 |

**典型工作流**（首次建表 / 每次改模型）：

```
在 models.py 定义模型
        ↓
python manage.py makemigrations   # 生成 0001_initial.py（记录"表长什么样"）
        ↓
python manage.py migrate          # 真正建表 + 写入 django_migrations 记录
        ↓
数据库表结构已更新
```

> 记住区别：**makemigrations 生成迁移文件（说明书），migrate 执行迁移（真正动数据库）**。改模型后漏掉 makemigrations，migrate 不会自动建新表；只跑 makemigrations 不跑 migrate，表也不会真的出现。查看迁移状态用 `showmigrations`（`[X]` 已应用 / `[ ]` 未应用）。

## settings.py 逐项解读

### 基础项

| 配置 | 作用 | 要点 |
|---|---|---|
| `BASE_DIR` | 项目根目录（Path 对象） | 拼路径用 `BASE_DIR / 'db.sqlite3'` |
| `SECRET_KEY` | 签名密钥（session、CSRF 等） | **生产环境必须保密、用环境变量注入** |
| `DEBUG` | 调试模式 | 生产必须 `False`，否则泄露堆栈 |
| `ALLOWED_HOSTS` | 允许访问的主机名列表 | 生产必须填写域名，否则 400 |

### INSTALLED_APPS

用于挂载`python manage.py startapp`创建的app和第三方app（第三方库）
三类应用按顺序排：

```python
INSTALLED_APPS = [
    # 自建应用
    'myapp',
    # 第三方应用
    'rest_framework',
    # Django 内置应用
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]
```

> `django.contrib.admin`（后台）、`auth`（认证）、`sessions`（会话）、`messages`（消息）等内置应用与 MIDDLEWARE 中的对应中间件成对出现，删掉会破坏对应功能。

### 中间件：MIDDLEWARE

请求→响应之间按顺序经过的钩子。默认七件套的作用：

| 中间件 | 作用 |
|---|---|
| `SecurityMiddleware` | 安全头、HTTPS 重定向、HSTS 等 |
| `SessionMiddleware` | 管理会话（cookie → session 数据） |
| `CommonMiddleware` | URL 末尾斜杠补全等 |
| `CsrfViewMiddleware` | CSRF 防护（模板必须有 `{% csrf_token %}`） |
| `AuthenticationMiddleware` | 给 `request.user` 注入当前用户 |
| `MessageMiddleware` | 一次性消息（messages framework） |
| `XFrameOptionsMiddleware` | 点击劫持防护（X-Frame-Options） |

顺序有讲究：Session 在 Auth 之前、Auth 在 Messages 之前，不要随意调换。

### 路由与模板

```python
ROOT_URLCONF = 'mysite.urls'   # 项目级 URLconf 入口

TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [],                       # 额外模板目录（如项目级 templates/）
        'APP_DIRS': True,                 # 是否在每个 app 的 templates/ 下查找
        'OPTIONS': {
            'context_processors': [       # 注入到所有模板的全局变量
                'django.template.context_processors.debug',
                'django.template.context_processors.request',
                'django.contrib.auth.context_processors.auth',        # {{ user }}、{{ perms }}
                'django.contrib.messages.context_processors.messages', # {{ messages }}
            ],
        },
    },
]
```

> `auth` context processor 提供模板里的 `{{ user }}` 与 `{{ perms }}`；`request` 处理器提供 `{{ request }}`（分页、当前路径等都要靠它）。

### 数据库：DATABASES

SQLite（开发零配置）：

```python
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
```

PostgreSQL（生产常用）：

```python
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': 'mydb',
        'USER': 'myuser',
        'PASSWORD': 'mypassword',
        'HOST': 'localhost',
        'PORT': '5432',
    }
}
```

### 密码校验 / 国际化 / 静态文件 / 主键

| 配置 | 作用 |
|---|---|
| `AUTH_PASSWORD_VALIDATORS` | 密码校验（与用户相似度、最小长度、常见密码、纯数字） |
| `LANGUAGE_CODE = 'zh-hans'` | 默认语言（中文站点） |
| `TIME_ZONE = 'Asia/Shanghai'` | 时区 |
| `STATIC_URL = 'static/'` | 静态文件访问前缀（生产再加 `STATIC_ROOT`） |
| `DEFAULT_AUTO_FIELD = 'django.db.models.BigAutoField'` | 主键类型（Django 3.2+ 默认） |

### 自定义设置

settings.py 是普通 Python 文件，可追加配置，代码里用 `django.conf.settings` 读取：

```python
# settings.py 末尾
LOGIN_URL = 'accounts:login'                    # 未登录跳转地址
LOGIN_REDIRECT_URL = 'learning_logs:index'      # 登录成功后跳转
LOGOUT_REDIRECT_URL = 'learning_logs:index'     # 登出后跳转
```

## 项目级 URL 路由

项目 `project/urls.py` 是 URLconf 入口，通常把各应用的路由用 `include()` 挂进来：

```python
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('accounts/', include('accounts.urls')),
    path('', include('myapp.urls')),
]
```
